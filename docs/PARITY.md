## Public release gates

- [ ] Every original user capability above has comparable tested behavior; intentional security changes documented explicitly.
- [ ] Backend adversarial review: path boundaries, races, authorization, resource exhaustion, unauthenticated setup, content serving, crash recovery and database/file consistency.
- [ ] Browser journeys on desktop and mobile, including keyboard navigation and accessible controls.
- [ ] Native clean install, restart, upgrade and rollback on supported OS/Node versions.
- [ ] Container built and tested with non-root Unraid UID/GID, persistent mounts and restricted capabilities.
- [ ] Final name selected after availability checks, original logo removed, own logo and install icons rendered and verified.
- [ ] Own OSI license and third-party notices complete.
- [ ] Public GitHub repository, security reporting, CI, update PRs and release artifacts verified live.
- [ ] Public image, tested Unraid XML, support destination and repository profile; validate/scan and submit through current Community Applications portal.
- [ ] Unraid listing accepted and externally verified; submission alone is not acceptance.

## Maintenance

Automated tests, scheduled dependency checks, update pull requests and a documented release procedure are required. They do not establish a promise that software is vulnerability-free. Dependency updates must be reviewed and tested before publishing an update. Do not silently enable self-updating application code on users' servers.

## Verification increment: shared links and editor preferences

On Windows/Node 24.14.1, 22 tests pass. `npm run test:package` and `npm run check` pass. Browser verification used disposable demo files: both editors adopted 20px text and a changed theme; unsaved contents and undo history survived. No production user files were used.

Move-recovery tests inject an interruption immediately before/after filesystem rename, close the app, reopen the same SQLite/storage directories and verify the links. These are controlled failure/restart tests, not a physical power-loss test. Recovery requires stable filesystem identity. Cross-filesystem moves now use staged copies and journaled publication/cleanup, with real Linux mount verification described below.

Trash/restore recovery now uses a separate SQLite intent journal. Same-filesystem renames reconcile the original object's identity; cross-filesystem transfers copy into reserved staging, record the completed copy, publish it, and then remove the source. Startup rolls back incomplete copies or completes published transfers. Trash metadata and link revocation commit together. Pending operations block mutations and affected public links until recovery; ambiguous identities stop startup without overwriting an unrelated destination. The 20 trash tests cover both directions, prepared/renamed/copying/copied/ready/published/removed interruptions, partial staging, partial recursive cleanup, actual server restart/link revocation, and a real Linux /tmp-to-/dev/shm transfer. All 72 tests pass in the restricted amd64 image, and the production native archive plus UID/GID 99:100 container smoke also pass. These checks simulate process interruptions, not physical power loss or hostile concurrent host writers. Ordinary file-manager moves across mount points are now covered by the separate move journal described below.

Runner labels are based on the [GitHub-hosted runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Configured CI is not evidence of a successful remote run.

Original proxy references: [nginx](https://github.com/silverwind/droppy/wiki/Nginx-reverse-proxy) and [Apache](https://github.com/silverwind/droppy/wiki/Apache-reverse-proxy). Both examples proxy the hostname root; this is not evidence of subpath support.

Cross-filesystem file-manager moves: the move journal now adds copy phases in a separate table, preserving existing pending same-filesystem records. Incomplete copies stay under reserved `.app-tmp-` directories; recovery rolls them back while retaining the source, or finishes publication/cleanup once a complete copy is recorded. Directory and child share paths change in the same transaction that completes the journal. Tests exercise partial copies, partial source cleanup, unrelated destination collisions and both filesystem directions. Three HTTP integration tests use two separate tmpfs mounts under the same shared root: normal transfer and interruptions after publication/removal. They restart the server, download through the existing public link, reuse the old path without redirecting that link, reject destination collisions, and move back across the mount boundary. The container CI job now supplies these mounts. Local Linux verification passes all 82 tests; Windows passes 77 with five mount/Linux-only checks skipped. Native-package and restricted UID/GID 99:100 container smoke checks also pass. Physical power loss, hostile concurrent host writers, and SMB/NFS behavior remain outside this evidence.

Unraid publication preparation now includes a metadata generator (`scripts/unraid-template.js`) and [deployment/review steps](UNRAID_PUBLICATION.md). Generated beta XML parses locally and rejects unsafe metadata inputs. No final identity has been applied, no registry/repository URLs have been invented for publication, and no submission or Unraid installation has occurred.

Branding: an original two-pane folder SVG and monochrome variant are available in docs/branding, with a responsive name comparison preview. These are proposals only; no name is selected and the runtime still needs its old identity/icons replaced after selection. Browser checks confirm all preview images load at 24/48/80 px and no horizontal overflow at the inspected 736 px viewport.

Single-instance recovery guard: an exclusive SQLite lock in the configuration directory is acquired before journal recovery. Tests reject a second app in the same process and a separate process while an upload is actively receiving, preserving that upload's temporary file. Normal close, failed startup and hard process termination release the lock; restart then succeeds without deleting a stale marker. The amd64 container smoke also starts a second container on the same volumes, verifies APP_ALREADY_RUNNING/nonzero exit and checks that the first container remains healthy. Current full-suite results are 92 passing Linux tests and 87 passing Windows tests with five Linux/mount-specific skips. Native package installation/switch/restore and restricted container runtime checks pass. This is per configuration directory and depends on working filesystem locking, not coordination between independent databases or network hosts.

Successful logout now calls the same cleanup as Stop: clear event handlers, pause, remove the source, reset the media element and queue, and remove the player bar. It also clears the in-app copy/cut selection. Unauthenticated initialization performs the same cleanup. Startup unlinks those recorded temporary names, never the final destination, and only then removes their records. Tests forcibly terminate a real child server during receiving, after staging and after publication, for both new uploads and replacements. Restart removes temporary files, preserves old destination bytes before publication, and retains complete new bytes after publication (including the hard-link publishing case). Untracked files in both temporary and shared storage remain untouched. Further tests reject a replaced parent junction/symlink and a malformed recovery identifier without removing unrelated contents. All 90 tests pass in the restricted Linux image; Windows passes 85 with five Linux/mount-only skips. Native-package and UID/GID 99:100 container smoke checks pass. Interrupted receiving uploads are discarded rather than resumed; after a client disconnect, inspect the destination before retrying because publication may already have completed. These are process-crash tests, not physical power-loss evidence. Existing untracked temporary files from older development builds are not automatically swept.
